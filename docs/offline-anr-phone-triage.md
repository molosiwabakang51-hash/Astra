# Offline Qwen3 1.7B — slow answers, blank responses and Android ANR

**Status: experimentally mitigated; no device-level ANR trace has been collected.**

The owner reported that local Qwen3 occasionally produces no response until a
retry, that replies have become slower, and that Android has displayed a
**"Wait / Close app" (Application Not Responding)** dialog. These symptoms are
release-blocking. A successful Gradle build does not demonstrate an ANR fix.

## Safe mitigations in this branch

- Durable generic JNI-inference checkpoints now write/clear in
  `Dispatchers.IO`, not on Android's main thread. Cancellation clears the
  marker in a non-cancellable IO block, while a fatal native process death
  still leaves the checkpoint for diagnostics. Prompt and answer text are
  never stored in the checkpoint.
- Streaming partial responses reach the Compose Markdown bubble at most
  around twice per second; unchanged/blank partials are skipped. The first
  usable partial is immediate, and **all native tokens are retained** in the
  existing final-answer buffer. This reduces redundant layout/repaint and
  auto-scroll load, without altering the model, GGUF or tokenizer.
- In-chat Retry also recognises reviewed `Offline model unavailable.`
  messages generated by the app's safe error mapper, and a completed
  interrupted-response marker. A retry does not silently erase notes/tasks
  or apply workflows.

These mitigations **do not** guarantee shorter native token latency, prevent
every C++ deadlock, make Qwen3 more intelligent, or prove the cause of a phone
ANR. We need an actual on-device reproduction and Android process evidence.

## Owner-phone acceptance — do not uninstall Astra to test

1. Keep an independent backup of existing chats/tasks/notes. Use only an
   installation compatible with the installed app's signing certificate and
   version. Never uninstall to force an unsigned/debug update.
2. In Settings, confirm Qwen3 1.7B is loaded and record the content-free
   inference timing and process-exit summary if shown.
3. Enable airplane mode. In a new chat, ask for a **brief** 2-sentence
   explanation of why bond prices fall when yields rise. Then ask the same
   question in a second chat. Record approximate cold-start and warm-start
   time and whether Android Back/scroll remain responsive.
4. Ask a longer educational question (`Explain modified duration with an
   example`) and scroll upward while the reply streams. The UI should
   remain interactive and must not jump back to the latest bubble until
   explicitly requested.
5. Stop an in-progress answer once; confirm the interrupted text remains
   clearly labelled. Tap **Retry last response** after a genuine failed or
   interrupted reply; verify it succeeds or returns an honest diagnostic
   rather than a stuck spinner.
6. If Android shows **Wait / Close app**, use **Wait** if safe, note whether
   a response eventually arrived, and record the exact stage shown on
   screen. After restarting, check Settings for the sanitized Android
   process-exit reason. An ANR notification without a captured trace is
   evidence of a freeze, **not** proof of which code path caused it.

A developer trace can help isolate whether the thread was blocked on
Compose rendering, preference writes, JNI, memory pressure or an OS service.
Android bug reports can contain private chat, device identifiers and app
data; **never upload an unredacted bugreport or broad logcat dump**. Share
only redacted, relevant ANR stack-thread sections after removing personal
text and file paths. Do not grant remote access.

An Android/JVM and Python CI pass is a merge gate, not a physical-device
pass. Retest under the actual phone's RAM and thermal conditions.
